This is a **continuation of Phase 2**, not Phase 3. The CRM foundation (data model, opportunity pipeline, assignment, duplicate detection/merge/undo, and a basic frontend) is complete, twice-reviewed (including an independent `fable-phase-reviewer` pass), tested (42/42 backend, 15/15 frontend), and checkpointed — see `docs/leadzaro/phase-2-completion-report.md`. The remaining items below were deliberately deferred per that report's own stated reasoning ("a coherent stop after item 3 or 4 ... is preferable to a rushed, unreviewed attempt at all nine") and per `docs/planning/06_PHASES_2_TO_8_ROADMAP.md` § "Phase 2", which this prompt is scoped against — re-read the current repository before trusting anything here, per the standing rule that prior reports are evidence, not live truth.

## What this slice of Phase 2 actually delivered (re-verify against current code, don't assume)

- `Opportunity`/`Contact`/`Location` models, all denormalizing `agencyOrganizationId` (never resolved via a join through the prospect organization) — see ADR 0006 for why. Any new Phase 2 entity attached to a prospect/client organization should follow the same pattern.
- `server/core/crm/pipelineCatalog.js` — `STAGES` (validated reference list), `CLOSED_STAGES`, `LEGACY_STATUS_TO_STAGE`. The scoring fields (`Opportunity.score`, `scoreReason`) already exist and are settable via `PUT /api/v1/crm/opportunities/:id`, but there is no dedicated scoring algorithm or UI — this is the most natural immediate next slice (item 4 below) since the schema is already there.
- `server/modules/crm/{opportunityService,opportunityController,mergeService,mergeController,routes}.js` — full CRUD/assignment/merge/undo, all permission-gated (`leads.read`/`leads.save`/`leads.archive`/`crm.manage_pipeline`/`leads.assign`), all audited.
- Frontend: `src/app/features/crm-pipeline/*`, `src/app/core/services/crm.service.ts`, `src/app/core/models/crm.model.ts` — a working, mobile-usable pipeline table. No Contact/Location management UI exists yet even though the backend models do (Contact/Location are currently only reachable through the merge flow and direct test fixtures) — building that UI is a prerequisite-in-spirit for several items below (a sales dashboard showing "contacts reached" needs Contact rows to actually be creatable by a human).
- Test helpers: `server/tests/helpers/factory.js` (`createOrganization`/`createRoleAssignedMember`/`loginAs`) and `globalSetup.js` (drops/recreates the test DB fresh every run) — reuse directly, don't rebuild equivalent setup.
- Known, documented backlog from the completion report (re-read it): Contact/Location management UI + a service-layer tenant-isolation assertion baked in from the start (currently an unenforced invariant that happens to hold); `aria-label` on badge-selects; Contact/Location dedup on merge; `findPossibleDuplicates` pagination if scale grows; a low-probability concurrent-double-merge race.

## Remaining Phase 2 outcomes (from the roadmap doc — verify scope against it directly)

1. **Opportunity/engagement scoring with manual override + reason** — schema exists; needs an actual scoring signal (even a simple rule-based one: reviews count, has-website, recency of contact, stage) and a clearer UI affordance than the raw number field the pipeline table currently shows.
2. **Sales employee dashboard and performance tracking** — per-rep/per-agency pipeline health (counts by stage, conversion rates, assignment load — the same load-count logic `roundRobinAssign` already computes could be reused/exposed), reusing Phase 1's existing `dashboard.service.ts`/`DashboardComponent` pattern where sensible rather than building a parallel one.
3. **Website audits + shareable report** — one per prospect; reuse the hashed-token pattern from Phase 1's invitations for the shareable link (`server/core/security` or wherever that token logic lives — check Phase 1's invitation service). No external audit-generation service is assumed to exist yet — build the adapter interface + a real, useful *rule-based* first version (e.g., has-website, mobile-friendliness heuristic, page speed if easily checkable) before assuming a paid third-party API, per the standing external-services rule.
4. **Public Website Guys landing pages + inbound forms + UTM/source attribution** — a genuinely separate surface: public (no-auth) Angular routes feeding the same `Opportunity`/`Contact` pipeline via a constrained public API (rate-limited, validated, no ability to read anything back). This is the lowest technical risk item but touches public-facing surface area — review CORS/rate-limiting/spam considerations before shipping.
5. **Manual/optional enrichment adapter** — external API; build the adapter interface + mock/disabled mode first, per the standing "external services" rule; do not block on missing credentials.
6. **Assisted outreach sequences requiring employee approval** — reuses `OutreachActivity` conceptually but needs a queued/approval-gated sequence concept; design this against the existing audit/notification infrastructure rather than a parallel one.
7. **Optional territories** — build the column/table but no enforcement UI yet if time-constrained (this was already flagged as optional-if-tight in the original Phase 2 plan).
8. **Saved search campaigns (private/shared)** — was mentioned in the original Phase 2 scope but not yet started; a `SearchCampaign`/`SearchCampaignMembership` model was sketched in `docs/leadzaro/current-phase-plan.md` § "Proposed data model" but never built this slice.
