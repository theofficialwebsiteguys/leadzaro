## What Phase 4 actually delivered (the foundation Phase 5 builds on — re-verify, don't assume)

- Every client `Organization` now has exactly one `Project` row (backfilled for pre-existing clients, created automatically for every future conversion via `ensureProjectForConversion`). A website this phase builds belongs to a `Project`, the same way Tasks/Messages/Files do — reuse that relationship, don't invent a parallel one.
- `ADR 0007`'s client-visibility enforcement architecture (`server/core/authorization/visibilityGuard.js` + `server/core/authorization/clientVisibleModels.js`) is the established, twice-battle-tested pattern for **any** model a client-membership request can reach: install the guard hook on the model, add every accessor to `clientVisibleModels.js`, never query the raw model elsewhere. A website/page/section schema is exactly this kind of model — client-owned, must never leak across organizations, and (per this phase's own editing-levels model) has its own finer-grained visibility question layered on top: which fields of a Basic-level client can edit vs. read-only vs. entirely hidden (Professional/Advanced-only settings). Re-derive that layering explicitly; do not assume Phase 4's exact `isClientVisible`-boolean shape transfers unchanged — Phase 4's gate was binary (client sees it or doesn't); this phase's is graduated (client edits some sub-set of what they can see, per editing level).
- Client-side "create/act" permissions (`messages.post`, `requests.create`, `meetings.request`, `files.upload`, `cancellations.request`) are granted broadly to every client role except `viewer` — the same pattern almost certainly applies to a website's Basic-level editing permission, with `viewer` again the one deliberate exception; verify this against whatever role/permission granularity the website builder actually needs (Basic/Professional/Advanced are themselves a permission-like distinction that may not map 1:1 onto the existing `CLIENT_ROLES` list — this needs its own design decision, not an assumption).
- The adapter-interface pattern (`EmailAdapter`, `EnrichmentAdapter`, `StripeAdapter`, `GoogleCalendarAdapter`, `StorageProvider`/GCS — abstract base, Mock/Disabled/Live subclasses, cached factory keyed by an env var) is now used five times in this codebase. Phase 5 itself needs no new external adapter (no code generation, no deployment, no real hosting yet — those are Phases 6/7), but the asset manager ("no-extra-service image optimization") should be evaluated against whether it needs a new adapter or can reuse the existing `StorageProvider`/GCS wiring from Phase 4.
- `recordAudit()`, `Notification`/`notify()`, `Invitation` are the established patterns for anything Phase 5 needs to audit or notify about (e.g. a client submitting a content edit for review, per this phase's "client content permissions and review rules" outcome).

## Phase 5 major gate

**The schema, preview renderer, and version history must be stable before Angular code generation is introduced** (this exact sentence is the roadmap's own major-gate wording — Phase 6 depends entirely on Phase 5's schema being trustworthy and versioned correctly). Concretely: no Phase 6 work should be able to reference a website's structure through anything other than the versioned schema this phase defines; a preview must render correctly from a given schema version alone (no hidden state); and version history (autosave, named checkpoints, compare, restore) must be provably lossless — restoring an older version must reproduce that version's exact prior state, not an approximation.

A secondary gate carried over from Phase 4's own major gate and this phase's own outcome list: **client editing permission levels (Basic/Professional/Advanced) must be enforced server-side**, exactly like every Phase 4 visibility/permission boundary — a Basic-level client attempting a Professional-level edit (e.g. via a crafted request bypassing the frontend UI) must be rejected by the API, not merely hidden from the editor UI.

## Phase 5 non-goals (do not start these)

Angular code generation itself (Phase 6 — this phase only needs to produce a schema stable enough for Phase 6 to later consume; do not generate real Angular component files from the schema this phase). Repository/GitHub/branch/deployment workflow (Phase 6/7). Production hosting, DNS, or real deployment of any generated site (Phase 7). SEO/analytics features beyond whatever minimal metadata the schema itself needs to carry for later phases (Phase 8). Full operational-transform live collaborative editing — master architecture § 14 explicitly says to use section-level locks/presence/autosave/named-versions/restore instead, not live co-editing, "initially."

At minimum, the escalation should resolve: the versioned-schema shape itself (how a "version" is represented — a full snapshot per version vs. a diff/event log, and how "compare"/"restore" are implemented against whichever choice is made); how editing-level enforcement maps onto the existing `CLIENT_ROLES`/permission-catalog model from Phases 1–4 (a new permission-per-level? a numeric level field on the membership? something else); and whether ADR 0007's guard-hook pattern extends cleanly to a schema that is versioned (does "client-visible" apply per-version, or only to the current published version?).
