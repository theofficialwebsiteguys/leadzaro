## CLAUDE.md rule 8 applies to this phase more directly than any phase so far

"Never perform production deployment, live DNS changes, real Stripe charges, destructive remote operations, or irreversible production migrations." Phase 7's own primary outcomes list is *entirely* production-deployment/DNS/hosting work. This is not a phase where that rule is a background constraint — it is the phase's own central tension: build real, complete, tested functionality for domain management, cPanel deployment, backup/rollback, and health checks, while the actual live actions those features perform must stay mock/disabled in this environment, exactly like every external adapter in this codebase already does (Stripe, Google Calendar, GCS, GitHub). Do not let "make it real" ambition cross into "actually register a domain" or "actually upload to a real cPanel account" — there are no real Namecheap/cPanel credentials in this environment by design, and none should ever be added without the user's own explicit action outside this session.

## What Phase 6 actually delivered (the foundation Phase 7 builds on — re-verify, don't assume)

- `WebsiteRepository` (`server/models/WebsiteRepository.js`) already holds `provider`/`externalRepoId`/`fullName`/`defaultBranch`/`status`, provisioned lazily on first real need. Phase 7's production deploy reads from this same repository — it does not need its own second repository concept.
- `WebsiteDeployment` (`server/models/WebsiteDeployment.js`) already has an `environment` column (`'preview'|'production'`), added specifically in Phase 6 so Phase 7 could extend this same table rather than introducing a second, competing deployment-history table — confirmed and recorded in Phase 6's own completion report. Verify this is still the right shape before widening it; the plan anticipated Phase 7 would widen `status` (currently `'pending'|'building'|'live'|'failed'` — this phase's own major gate, "restore the prior live build," almost certainly needs a `'rolled_back'` status and a pointer to the prior live deployment/backup) and add backup/health-check fields via a follow-on migration, not a new model.
- The generator (`server/core/codegen/generateWebsiteFiles.js`) produces real, `tsc`-verified-compiling Angular output from a specific immutable `WebsiteVersion.schema`, already used by both `websiteCodegenService.generateAndCommit` (commit to a branch) and `websiteDeploymentService.deployToBranch` (branch + commit + GitHub Pages preview + a `WebsiteDeployment` row). Phase 7's production build reuses this same generator — it is not a different code path that happens to also produce Angular files; re-derive what's actually different about a *production* build (a real `ng build` step producing a deployable dist bundle, almost certainly, rather than just committing source) rather than assuming the existing preview pipeline already covers it.
- The adapter-interface pattern (`GitHubAdapter` — the newest instance, `server/core/integrations/github/githubAdapter.js` — plus Stripe/Google Calendar/GCS before it) is now used 6 times and is the mandatory shape for this phase's own two new adapters: a **Namecheap adapter** (domain records/ownership metadata, renewal tracking) and a **cPanel adapter** (shared-hosting upload, document-root mapping, backup). Both need real Mock/Disabled/Live implementations with genuinely stateful mocks (matching `MockGitHubAdapter`'s precedent — a real in-memory domain-record/hosting-account simulation, not a stateless stub), since this environment will only ever exercise the mock.
- `recordAudit()` / `Notification`/`notify()` are the established patterns for this phase's own audit trail and "critical production, billing, domain, and security alerts cannot be completely hidden from responsible roles" requirement (architecture §21).
- ADR 0007's client-visibility architecture applies to any new client-reachable model this phase introduces exactly as it has 5 times before. Note Phase 6's own precedent: deployment/handoff-shaped data was made *employee-only* (`assertEmployeeContextForDeployment`/`...ForHandoff` in `clientVisibleModels.js`) — re-derive explicitly whether this phase's own new models (domain records, production deployments, backups) should follow the same employee-only pattern, or whether a client legitimately needs read access to some subset (e.g., "is my site live," "when does my domain renew") — don't assume either answer without deciding it explicitly and recording why, the same discipline Phase 5 and 6 both applied to every new model.

## Phase 7 major gate

**A failed or unhealthy production deployment must restore the prior live build without losing the domain, configuration, or form functionality.** This is the roadmap's own exact wording. Concretely: a production deploy that fails validation or a post-deploy health check must trigger an automatic rollback to the immediately-prior live build (architecture §16's own sequence names "Backup current cPanel folder" as a required step before "Upload new build," precisely so this rollback has something real to restore from) — and the domain's DNS/hosting configuration and any live form-submission routing must survive that rollback intact, not just the site's static files.

## Phase 7 non-goals (do not start these)

Actually registering a domain, actually changing live DNS records, actually uploading to a real cPanel account, actually charging for domain renewal — none of these can happen in this environment and must stay behind Mock/Disabled adapter implementations, per CLAUDE.md rule 8 (this is the single most important non-goal in this entire roadmap — read the section above again before writing the Namecheap/cPanel adapters). SEO features beyond the hybrid-analytics/Google-Analytics-connection outcomes explicitly listed above (Phase 8). Any AI provider integration (Phase 8, "optional AI provider interface"). Real Google Analytics account creation (guided *connection* to an account the agency/client already has is in scope; provisioning one is not).
