## What Phase 5 actually delivered (the foundation Phase 6 builds on — re-verify, don't assume)

- `Website.draftSchema` / `WebsiteVersion.schema` is the stable, versioned, schema-first source of truth this phase generates Angular code *from* — never treat it as provisional or re-derive an alternate representation. Shape: `{ pages: [{ id, route, title, sections: [{ id, componentKey, variant, settings, content }] }], navigation, siteSettings, organizationContent }`. A section's `content` holds human-facing values (text/richtext/image, and a form's own `fields`/`submitTarget`); `settings` holds structural/style properties (layout pickers, numeric spacing/opacity) — this split was corrected during Phase 5's own closing review (see the completion report's Security and privacy section) specifically so a schema consumer can rely on it; verify your own reads against `server/core/websites/websiteCatalog.js`'s `CONTENT_PROPERTY_TYPES` rather than re-guessing the split.
- `SectionDefinition` (`server/models/SectionDefinition.js`) already has a `state` field (`managed`/`extended`/`registered_custom`/`detached`) reserved by Phase 5 specifically for this phase to give real meaning to — Phase 5 only ever set/read it as inert data. This is very likely your component-state model for "managed, extended, registered, and detached component states" (a Phase 6 primary outcome) — verify this mapping explicitly rather than inventing a parallel field.
- `SectionDefinition` also has a separate `status` lifecycle (`draft`/`published`/`deprecated`, added in Phase 5 slice 8) for library-governance purposes — do not conflate this with `state` above; they answer different questions (is this offered for new use vs. what kind of component is it).
- ADR 0007's client-visibility enforcement architecture (`server/core/authorization/visibilityGuard.js` + `clientVisibleModels.js`) is the established, now four-times-battle-tested pattern (Phases 1, 4, and 5 twice) for any model a client-membership request can reach. If this phase introduces new client-reachable state (e.g. a generated-repository record, a deployment-preview record), it goes through this exact pattern — install the guard hook, add accessors to `clientVisibleModels.js`, never query the raw model elsewhere.
- The adapter-interface pattern (`EmailAdapter`, `EnrichmentAdapter`, `StripeAdapter`, `GoogleCalendarAdapter`, `StorageProvider`/GCS — abstract base class, Mock/Disabled/Live subclasses, cached factory keyed by an env var) is now used five times in this codebase and is almost certainly the right shape for this phase's **GitHub adapter** (§16: "Namecheap/cPanel/GitHub/GCS integrations must use adapter interfaces") — this environment has no real GitHub App/OAuth credentials, so the Mock/Disabled split matters even more here than in prior phases: the mock adapter needs to simulate enough of a real repo/branch/PR lifecycle for the rest of this phase's workflow to be genuinely testable against it, not just a stub that returns fixed strings.
- `recordAudit()` / `Notification`/`notify()` are the established patterns for anything this phase needs to audit (a promote-to-development checkpoint, a merge-back, a production deploy click) or notify about (assigned roles on preview-ready, a designer/developer handoff).
- Phase 5's `WebsiteVersion` immutable-snapshot-per-version model is almost certainly what this phase's "design version ↔ commit ↔ deployment linkage" links a Git commit *to* — re-derive the actual linkage design rather than assuming a specific column name, but do not invent a second, parallel version-history concept.

## Phase 6 primary outcomes (from the roadmap — verify scope against it directly)

- Developer-quality Angular generation (typed, matching the `src/app/{generated,components/standard,custom}` split in architecture §15).

- Repository creation when design begins (§16).

- Branches and preview workflow.
- GitHub Pages automatic previews.
- Promote-to-development checkpoint/handoff (§16: named design checkpoint, activate development branches, technical handoff documentation, tasks for custom requirements, deploy a preview, notify assigned roles, preserve the builder version).
- Managed, extended, registered, and detached component states (very likely `SectionDefinition.state`, already reserved — see above).
- Custom component editor schemas.
- Component publication permission/review.
- Design version ↔ commit ↔ deployment linkage.
- Developer merge-back workflow.
- Protection against overwriting custom code.

## Phase 6 major gate

**A designer edit must never overwrite developer-owned custom functionality, and a registered developer component must remain usable in the builder.** This is the roadmap's own exact wording. Concretely: once a component/section has been promoted to a developer-owned state (`extended`/`registered_custom`/`detached` — Phase 5's reserved `SectionDefinition.state` values), a subsequent designer-side schema edit through the builder must be provably incapable of clobbering that developer's custom code, and that same registered component must still render/function correctly inside the builder's own preview and editing surfaces. Both halves of this gate need their own explicit test, not just a happy-path "generation succeeded."

## Phase 6 non-goals (do not start these)

Real production deployment, live DNS, or an actual cPanel upload (Phase 7 — this phase's own scope ends at preview deployment to GitHub Pages and the promote-to-development handoff; "Production deployment is manual" per architecture §16 and is Phase 7's concern). SEO/analytics features (Phase 8). Real Stripe charges, live third-party credentials of any kind — CLAUDE.md's permanent rule 8 applies to this phase specifically given its deployment-adjacent scope: no live DNS changes, no irreversible production operations, ever, in any phase.

## Before writing code

1. **Escalate the Angular-generation design, the generated/custom code-boundary mechanism, and the GitHub adapter's mock-fidelity design to `fable-phase-reviewer` before writing any migration or generator code.** This phase's major gate is explicitly an authorization/data-integrity boundary (a designer must not be able to destroy developer work) plus a major architecture decision (how generated code is actually produced and where the generated/custom line is drawn) plus a new external adapter and source-control/deployment surface — CLAUDE.md's escalation rule names all of these categories explicitly (major architecture, code-generation, source-control, deployment). At minimum, the escalation should resolve: how "generated" vs. "custom" is actually distinguished on disk/in the repo (a directory boundary per architecture §15's own example tree, enforced how — a generator that refuses to touch `custom/`, a file-ownership marker, something else); what a "registered" or "detached" component concretely means for what the generator does and does not touch; how the GitHub adapter's mock mode simulates enough of a real repo/branch/PR/Pages-deploy lifecycle to make the rest of this phase's workflow genuinely testable without live GitHub credentials; and how `WebsiteVersion` links to a Git commit without inventing a second, competing version-history concept.
2. Re-run Phase 5's acceptance gates once more to confirm nothing has drifted (`npm run test:backend`, `ng test`, `ng build`) — a fresh phase boundary's job even if this prompt says they passed.
3. Produce `docs/leadzaro/current-phase-plan.md` (overwrite — it's a per-phase working document; every prior version is preserved in git history) with an evidence audit and acceptance matrix before writing the first migration.
